# Pilot quality targets and operations

Nonfunctional requirements (NFRs) describe quality and operating limits. These are targets and gates, not achieved results. The user approved a free hosted pilot on 30 September 2026. [ADR-0005](../decisions/0005-free-pilot-operations.md) records the tradeoff.

## Workload and measurement

Target workload: 100 accounts, one per user; 100,000 saved prospects total (1,000 per account); 20 concurrent dashboard users; 100 connected extensions. Include list memberships, revisions, rendered approvals, observations, attempts, indexes and retained campaign history in storage measurement. Prospect count alone cannot prove a 500 MB database fits. Generate synthetic data with representative text sizes and long-running history growth; no copied private inbox data.

Measure warm paginated API reads at page size 50 (maximum 100) with realistic filtering and tenant guards, from India and North America against the Canada (Central) pilot setup. Record p50/p95/p99, error rate, sample count and at least 30 minutes of steady workload after warm-up. Warm p95 must be <=1.5 seconds in each region. Report cold starts, provider outages and failed requests separately AND in overall availability/error figures; never discard failures to improve latency claims. Define reproducible clients/regions and exact fixtures before foundation Ready.

| --- | --- | --- | --- |

| Security | Every object access tenant-guarded; no browser privileged secrets; executor revocation enforced | Cross-tenant API/RLS/grant tests and bundle/config review before hosted admission | Not tested |

## Provider constraints and admission guards

These primary sources were checked on 30 September 2026. Limits may change and must be checked again before provisioning; the [pilot operations design](pilot-operations.md) records a later check.

| Service | Documented free constraint | Design consequence |
| --- | --- | --- |
| [Cloudflare Pages pricing](https://developers.cloudflare.com/pages/functions/pricing/) | Static asset requests free/unlimited; dynamic functions metered | Static dashboard hosting does not make the API free of request limits |
| [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) | 100,000 requests/day; 10 ms CPU per invocation; network waiting is not CPU | Batch bounded queries; measure CPU, not just latency; no heavy export/backup work in request handler |
| [Supabase pricing](https://supabase.com/pricing) | 500 MB database, 5 GB egress, 50,000 MAU, 500,000 Edge invocations/month, two active projects; pause after one week inactivity; no automatic backups or uptime SLA | Workers is our API, not Supabase Edge; neither Edge allowance nor MAU proves database capacity |
| [Supabase backups](https://supabase.com/docs/guides/platform/backups) | Free projects should keep off-site exports; automated daily backups on paid plans | Operator owns encrypted off-site backup/export and restore drills |
| [Default Auth SMTP](https://supabase.com/docs/guides/auth/auth-smtp) | Only team-authorized addresses, two emails/hour, not production | Do not assume free production email delivery; use [Google OAuth](https://supabase.com/docs/guides/auth/social-login/auth-google) setup later |

Provisional request budget: idle extension poll/heartbeat combined at most once per five minutes with jitter, only while browser connected (100 continuously connected extensions => 28,800 calls/day). Active execution uses bounded request batches and a shared token bucket, never a one-second polling loop. Dashboard uses explicit refresh or polling no faster than 60 seconds while visible, stops when hidden, and caps total page requests per user/session. Twenty continuously visible dashboards at one request/minute add 28,800/day before pagination and mutations; therefore all paths share measured quota budgets. Scheduler at most every five minutes adds 288 invocations/day. These are rough budgets, not a load result; Auth/database/provider traffic and egress require separate measurement.

Use observation batches of at most 50 records and 128 KiB, page maximum 100, bounded queue scans of at most 50 actions, indexed queries and per-tenant rate limits. Exponential retry backoff with jitter starts at 30 seconds and caps at 15 minutes for failed polling; offline clients wait for connectivity. Never retry sends via transport retries; only idempotent API reconciliation can retry. Keep a five-minute global request budget and daily budget enforced centrally, with no independent per-campaign quota that multiplies requests. Avoid high-frequency polling to compensate for missing observation capability.

Initial operating thresholds: warn at 60% of any provider quota or projected daily/monthly usage; deny new admission/import/growth and new send authorization at 70%, leaving 30% reserved for stop, result/reconciliation, authenticated export/delete and recovery. For the database, include indexes and overhead: 70% of 500 MB is 350 MB, not 350 MB of prospect fields alone. Measure Workers CPU p95 <=5 ms and p99 <=8 ms on representative operations; any repeated 10 ms limit failures blocks rollout. Requests must stay below 70,000/day in the ordinary workload budget; measure monthly egress against a 3.5 GB ordinary budget. These provisional gates may force a much smaller pilot.

Quota meter stale for more than 15 minutes or missing reliable usage estimate means block new growth/sends until refreshed. Storage forecast includes retained history; reserve for outstanding outcomes before granting authorization. Hard application limits enforce <=100 users and <=1,000 prospects per account transactionally even when quotas are healthy. Stop/result/export/delete paths get priority and bounded streaming/jobs, but provider-wide outages or exhausted provider quotas can still make them unavailable; the UI must report this rather than promise an impossible reserved channel. Local stop remains available in the extension. Never silently delete history, lower evidence quality or automatically upgrade paid services to recover headroom. Pause admission early and request an explicit upgrade decision if measured capacity cannot fit.

## Retention, export and deletion

Keep prospect lists and campaign history until the user deletes them; no silent quota-based expiry. Retain only selected fields and minimum observation metadata needed to explain actions. Do not store incoming message bodies, full inbox archives, LinkedIn credentials, raw pages or private content in technical logs. Approved rendered outgoing content belongs to user-controlled campaign history.

Technical-log retention was provisionally 14 days. Reconciled on 20 October 2026 in the [pilot operations design](pilot-operations.md): bounded auth denial/dependency audit records in the database keep the implemented 30-day retention, Workers platform logs keep the provider's three-day Free retention, and aggregate content-free usage/error metrics are retained for 90 days. The 14-day figure is superseded. Logs use opaque IDs, event types, latency, status and uncertainty reasons; redact tokens, names, profile URLs and message text. User deletion removes linkable operational identifiers where practicable; the deletion ledger below is narrowly retained for backup erasure only.

Authenticated export includes the owner's retained prospects, lists, campaign revisions/approvals, states and action history in a portable documented format. Exports are encrypted at rest, access-scoped and expire after 24 hours; operator-provided encrypted streaming export is the fallback if free storage cannot support temporary artifacts. Foundation refinement must select and test the exact export path before pilot admission. Deletion reauthenticates the owner, stops/fences execution, revokes executors, removes live data and product Auth identity within a target of seven days, and reports progress. Stop/result processing must not resurrect deleted content. Explain that deleting product records does not withdraw LinkedIn invitations or remove messages on LinkedIn.

## Backup custody and safe restore

Named pilot operator owns a daily consistent PostgreSQL export and required schema/migration/version metadata. Store encrypted off-site under operator custody, separate from the production provider/account; keep keys separately, access restricted, and no credentials in this repository. A free existing user-approved storage destination must be chosen before admission; this document does not create one or promise unlimited free backup space. Supabase Auth configuration/identity recovery requirements and exports need an explicit tested runbook; no assumption that a database dump alone recreates OAuth setup or external secrets.

Backup age target <=24 hours; retain rolling encrypted backups for seven days, then delete them. Record completion time, checksum, size and restore-check result without private content. If a backup is missed or cannot be verified, alert operator, mark degraded recovery and block new admission and sends until a good backup exists; allow priority stop/outcome/export/delete. Restore target <=4 hours is measured from operator-declared recovery start and includes validation before service resumes, not an uptime guarantee or automatic failover promise. If either target is missed, record actual age/duration and revised recovery estimate.

Record deletion tombstones outside the production backup set in a minimal encrypted ledger (opaque tenant ID, deletion time and backup cutoff). Immediately erase affected off-site snapshots where practical or ensure they expire within seven days; tell the user the remaining erasure window. Retain each tombstone until all containing backups are destroyed and any restore reconciliation completes, then remove it. Never restore a snapshot without applying later tombstones before access; no deleted user data returns to the pilot. Verify export artifacts are also removed. Backups that cannot satisfy this handling cannot be used for pilot data.

Restore in isolation, validate schema/grants/RLS and checksums, apply deletion ledger, then start globally paused with all old leases/executors revoked. Identify all actions since backup cutoff and any potential sends missing from backup using local journals and fresh verified observations; keep ambiguous accounts held. Reapprove changed/stale intent before resuming at ordinary spacing. Restoring a queue is never permission to replay it. Prove this using synthetic crash, late outcome and deleted-user fixtures before execution gates.

## Monitoring and operator response

Monitor API error rates/latency including failed requests, oldest due queue age, stale observation count/age, uncertain outcomes, connected executor heartbeat age, request/CPU/DB/egress usage and backup age. Initial alerts: API errors >5% over five minutes with >=20 requests, any uncertain send, backup older than 24h, quota warning above 60%, active executor missing three five-minute heartbeats, or eligible due work delayed >30 minutes during working hours with a connected executor. Waiting for acceptance/offline/paused work is shown separately, not counted as a scheduler failure. Operator investigates uncertainty before enabling that account's sender; no automatic clear-on-timeout.

Pilot operator maintains allowlist, capability flags, version revocations, backup checks and incident notes; user controls content approval and pause/stop. Infrastructure failures stop new sends and surface an honest status. Public availability commitments, paid plans, Web Store publication and automatic scaling expenses require later approval. No NFR in this document is established solely by writing it down.
